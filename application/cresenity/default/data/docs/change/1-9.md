- CServer
  - New `CServer_Certbot`, reachable as `CServer::server($ssh)->certbot()` — manages certbot as software rather than as certificates. `getVersion()`/`isInstalled()` (probing with `command -v` so it does not depend on shell error wording, which differs between distributions), `getInstallMethodList()` reporting which package managers the server actually has (snap, apt, dnf, yum), `getInstallCommand($method)` returning the exact commands **separately** from `install($method)` so a UI can show them before running anything, `getCertificateList()` parsing `certbot certificates` into name/domains/expiry/days-remaining/path, `renewDryRun()`, `renew()`, and `getAutoRenewStatus()` which checks for a systemd timer *and* a cron entry, since certbot installs one or the other depending on how it was installed. Distinct from the existing `CServer_LetsEncrypt`, which places certificate files and webroot challenges — its `isInstalled()` only answers whether the binary exists
  - `CApp_Navigation_Helper::nav()` no longer fatals outside an HTTP request. It opened with `c::router()->getCurrentRoute()->getRouteData()`, and `getCurrentRoute()` is null in CLI, console commands, and tests — so any attempt to render navigation there died with "Call to a member function getRouteData() on null". Route data is only used to work out which entry is *active*, so its absence now simply means nothing is marked active rather than taking the whole render down. This makes navigation rendering testable from CLI, which is how the callback fix above was finally verified end to end
  - **Fixed `CApp::renderNavigation()` never applying the navigation callback.** `CNavigation_Data::setNavigationCallback()` has existed as the documented way for an app to transform its whole nav array, but the method that actually renders the sidenav read `$this->nav` directly and, when that was null (the default), resolved the nav file itself — never going through `CNavigation_Data::get()`, which is the only place the callback is applied. Since `@CAppNav` compiles to `renderNavigation()` and is how essentially every app renders its sidenav (advokatweb, aidnity, apcpoin, devcloud …), the callback was silently a no-op on the one path that matters; it only worked through `CNavigation_Manager::render()`/`CApp_Navigation::render()`, which those apps do not use. `renderNavigation()` now falls back to `CNavigation_Data::get()` when no nav is set explicitly, so registered callbacks take effect. An app that passes a nav explicitly, or has called `setNav()`, is unaffected, and the result is memoised per domain so no extra file read is introduced. Found while making devcloud swap its sidenav for a per-server menu — the callback was registering correctly and simply never being consulted
  - **`CServer_OSAbstract` filled in.** It had been an empty abstract class (literally `abstract class CServer_OSAbstract {}`) since it was added; there was no remote-distro awareness anywhere — `CServer_OS` only reports the OS of the *local* PHP process, and `CServer_Server::getOS()` returns `PHP_OS` or a config value, neither of which says anything about the machine at the other end of the SSH connection. It now holds the per-distribution knowledge that every checker was otherwise guessing at with shell conditionals: `getPackageManager()`, `getInstallCommand($package)`, `getServiceUnit($service)` (Apache is `apache2` on Debian and `httpd` on RHEL; Redis is `redis-server` vs `redis`; cron is `cron` vs `crond`), and `getConfigPathList($software)`. Concrete `CServer_OS_Debian`, `CServer_OS_RedHat`, and `CServer_OS_Unknown`, selected by `CServer_OSAbstract::detect($server)` reading `/etc/os-release` on the remote and matching on `ID` **and** `ID_LIKE`, so derivatives (Rocky, AlmaLinux, Linux Mint) resolve without being listed. `CServer_OS_RedHat` picks `yum` below version 8 and `dnf` from 8 up. `CServer_OS_Unknown` deliberately returns null/empty rather than guessing, so callers fall back to probing instead of running a command that may not exist. Reachable as `CServer::server($ssh)->distro()`, cached per server
  - `CServer_Certbot` and `CServer_Redis` now consult the distribution rather than only probing: certbot orders its install methods with the distro's own package manager first (so a CentOS box is not offered APT merely because it happens to be present), and Redis looks for `redis.conf` at the distro's location first and checks the distro's service unit name first. In both cases the existing probe still decides — the distro only sets the order and the first candidate — because software installed from source often ignores its distribution's conventions
  - New `CServer_Redis`, reachable as `CServer::server($ssh)->redis()`. Most of what is worth knowing about a Redis instance only comes out of `INFO`, which needs authentication when `requirepass` is set — so the class **reads `requirepass` out of the server's own config file** when no password is passed, rather than returning an empty page for no visible reason. Provides `getVersion()`, `getServiceStatus()` (mapping the `redis`/`redis-server` unit names), `getConfigFile()`, `getInfo($section)` parsed into key/value, `getConfig($pattern)` (un-interleaving `CONFIG GET`'s alternating name/value output), `getKeyspace()` returning keys/expires/avg-ttl per database, and `getWarningList()` for the things that only show up here but can take a server down: `maxmemory` left at 0 so Redis grows until the machine runs out of memory, `noeviction` on top of that so writes get refused instead of making room, no persistence at all, a large number of unsaved changes, and listening on all interfaces without a password
  - New `CServer_WebServer`, reachable as `CServer::server($ssh)->webServer()`. `inspect()` returns **all** web servers present rather than a single answer, because one machine can run several at once — a real case: LiteSpeed holding 80/443 while nginx is installed and active behind it. Reports version, service status (mapping the differing unit names `lsws`/`lshttpd`/`openlitespeed`/`nginx`/`httpd`/`apache2` onto one type each), config path, virtual-host count, and — importantly — the ports each one is **actually listening on**, matched to the owning process, so it is visible which of them really serves requests. Also `getVirtualHostList($type)` reading LiteSpeed `vhconf.conf` or nginx `sites-enabled`/`conf.d` for domain and document root, `testConfig($type)` (`nginx -t` / `apachectl configtest`; LiteSpeed has no equivalent and returns null), and `reload($type)` which reloads gracefully — restart is deliberately not offered, since reloading is enough for a configuration change while a restart drops live connections
  - `CServer_Php::inspectAll($server)` — discovers **every** PHP on a server in one command, not just the default binary: package-manager binaries (`php`, `php7.4` … `php8.5`), LiteSpeed's `lsphp*`, and php-fpm services, returning version, loaded `php.ini`, the ini settings that actually govern application behaviour (`memory_limit`, `max_execution_time`, `upload_max_filesize`, `post_max_size`, `date.timezone`, `opcache.enable`), and the loaded extension list per binary. Symlinks are resolved with `readlink -f` so `php` and `php8.3` are not counted twice, and everything is gathered in a single command because each SSH round trip is expensive. Also `CServer_Php::isEndOfLife($version)`, decided from the major-minor number rather than a date table that would need constant updating
  - `CServer_Server::php()` now accepts a binary (`php('/usr/local/lsws/lsphp84/bin/php')`) and caches one instance per binary, so a single server handle can hold several PHP versions at once. The previous single `$phpInstance` cache always returned the default binary regardless of the argument. Calling `php()` with no argument behaves exactly as before
  - `CServer_Mail` also reports the **outbound relay**. Cloud providers routinely block outbound port 25 — DigitalOcean among them — so a mail server hosted there cannot deliver directly and must hand off to a third party. Reading `relayhost` (and whether SMTP auth to it is enabled) turns "why is nothing being delivered" from a hunt into a fact on the page; the host is matched against the common providers (Mailjet, SendGrid, SES, Mailgun, Postmark, SparkPost, Microsoft 365, Zoho, Brevo) so the answer reads as a name rather than a hostname. The SASL password file is deliberately **not** read — only whether auth is configured
  - New `CServer_Mail`, reachable as `CServer::server($ssh)->mail()`. Reports the MTA (postfix/exim/sendmail), the IMAP/POP server (dovecot/cyrus), and which mail ports are actually **listening on a public interface**, matched to their role (smtp/submission/imaps/…). The public-interface distinction is the point: nearly every distribution installs a local MTA purely so cron can mail root, so "postfix is installed" says almost nothing — what separates a real mail server is whether it answers on 25/465/587/143/993 from outside, and a bind on 127.0.0.1 is deliberately not counted. Everything is gathered in one command (`ss -ltnp`, falling back to `netstat` on older systems) since each SSH round trip is expensive
  - **SSH key pair generation, which the framework had nowhere.** Nothing under `system/libraries/` could produce a key pair — `CServer_SSHRepository` only opens connections from credentials that already exist, and `CRemote/` held just the SSH client. Two entry points, because the two cases are genuinely different. `CRemote_SSH_Key` generates on the machine PHP runs on: `generate($type, $bits, $comment, $passphrase)` returning private/public/fingerprint/type/bits, `inspectPublicKey($line)` reading type, bits, comment and SHA256 fingerprint back out of a pasted public key (so a key entered by hand records the same details as a generated one), plus `typeList()`/`bitsList($type)` as the single source for what is valid. `CServer_SshKey`, reachable as `CServer::server($ssh)->sshKey()`, does the same **on the target server** — for a key that should never travel the network in private form — and adds `addAuthorizedKey($publicKey, $user)`, which is idempotent (`grep -qxF` first) so it can be called repeatedly without stacking duplicate lines. It reuses `CRemote_SSH_Key`'s type/bits definitions rather than restating them. Both shell out to `ssh-keygen` instead of assembling keys from openssl: OpenSSH wraps its private keys in its own container format, and hand-rolling it is an easy way to produce a key that looks right and is rejected in use — and the fingerprint then matches what the server itself reports, byte for byte. Both write to a temporary directory and delete the private key afterwards whatever happens (a `finally` locally, an unconditional `rm` in the remote script), since the failure worth designing around is a private key left lying in `/tmp`
  - `CServer_Exception` now extends `CException` (it was a bare `extends Exception` with no subclasses and no usages), and a new `CServer_Exception_*` family carries the detail a caller needs instead of only a sentence: `UnsupportedKeyTypeException` (`getType()`, `getSupportedTypeList()`), `InvalidKeyBitsException` (`getBits()`, `getType()`, `getValidBitsList()` — valid sizes depend on the key type), `CommandNotFoundException` (`getCommand()`, `isLocal()` — "ssh-keygen not found" means something quite different on the app server than on the user's server), `KeyGenerationFailedException` (`getOutput()` keeping the raw command output separate from the short user-facing message) and `InvalidPublicKeyException` (`getPublicKeyPreview()`, truncated — a public key is not secret, but copying it whole into an error message only fills logs without explaining anything)
  - **`CServer_Certbot` can now issue certificates, not just manage them.** It could install certbot, list what it already held, and renew — but there was no way to obtain a certificate in the first place. `issue($domainList, $webroot, $email, $dryRun)` runs an HTTP-01 (`--webroot`) order, with `getIssueCommand(...)` exposed separately so a UI can show the exact command first, matching how `getInstallCommand()` already works. `--webroot` rather than `--standalone` on purpose: standalone has to bind port 80, so it means stopping the web server on a machine that is currently serving. `normalizeDomainList()` lowercases, strips scheme and trailing dots, de-duplicates, and drops what HTTP-01 provably cannot satisfy — wildcards (DNS-01 only), `_`, `localhost`, malformed names — because Let's Encrypt counts five failed validations per hour per domain against you whether the failure was interesting or a typo. `extractError()` pulls the two or three meaningful lines out of certbot's very long output. `--keep-until-expiring` means re-running for an existing certificate is a no-op rather than burning a fresh issuance
  - **Fixed `CServer_SSHRepository` caching connections by `host:port:username` only, ignoring the timeout.** The first connection to a server in a request therefore fixed the timeout for every later one: a quick status check (typically 10s) runs first, and the genuinely long command that follows — installing a package, issuing a certificate — silently reused it. The failure mode is the nasty kind: no error, just output truncated mid-stream while the command carries on to completion on the server, so a successful operation reads as a failure. Found when a certbot `--dry-run` taking 8.6s tipped over 10s as soon as account registration was involved, and the caller saw the run stop after "Simulating renewal…" with the concluding "The dry run was successful." never arriving. The timeout is now part of the cache key, so configs differing only in timeout are correctly separate connections
  - **Renewal now passes `--no-random-sleep-on-renew`.** Run non-interactively, `certbot renew` sleeps a random delay of up to ten minutes before doing anything — correct for cron, so the world's servers don't all hit Let's Encrypt on the same minute, and completely wrong for a button a person just pressed: the page hangs and then fails on the connection timeout while certbot has not yet done a thing. Diagnosed from a renewal that sat for minutes with no output, whose log read "Non-interactive renewal: random delay of 469.87 seconds". The flag is accepted by certbot 1.21 and 2.9 (it is absent from `--help` output, which is why it is easy to miss). This affected the existing whole-server renew button too, not just the new per-certificate one
  - **`CServer_Certbot` now runs certbot through `sudo -n` when the connection is not root** — and, just as importantly, stops reporting a permission refusal as "no certificates". certbot writes to `/etc/letsencrypt` and `/var/log/letsencrypt`, so it refuses to run as an ordinary user, and many cloud images only offer a non-root login (`ubuntu`, `centos`, `ec2-user`) with passwordless sudo. On such a server `certbot certificates` returned `Permission denied: '/var/log/letsencrypt/.certbot.lock'`; `getCertificateList()` parsed that text, found no certificate blocks, and returned an empty array — so the UI stated the server had no certificates at all. It had two. The prefix is probed once per instance (`id -u`, then `sudo -n true`) and is empty for root connections, so nothing changes there; it is applied to `certificates`, `certonly`, `renew`, `delete`, and the install commands. A permission refusal now throws `CServer_Exception` instead of returning an empty list
  - `CServer_Certbot` renewal and deletion made per-certificate. `renew($certName, $force)` and `renewDryRun($certName)` now take an optional lineage name — previously both were all-or-nothing — with `getRenewCommand()` exposed for the show-the-command-first pattern, and `delete($certName)` removes a certificate together with its renewal config. `delete()` checks the name exists **before** running (certbot only complains vaguely about a typo, and deletion cannot be undone) and confirms afterwards by re-reading the list, because certbot does not reliably exit non-zero on failure. Also dropped `--quiet` from renewal: the output is the only way a caller can tell what happened, and an empty result page made a successful renewal and a no-op look identical. Note the deliberate absence of `--force-renewal` on the plain path — `certbot renew` only touches certificates inside the 30-day window, and that is the correct behaviour rather than something to work around; forcing is a separate call because it spends Let's Encrypt's five-duplicates-per-week allowance
  - New `CServer_Exception_InvalidDomainException` (`getReason()`, `getDomainList()`), kept distinct from a certbot failure because it is detected *before* anything runs — so it costs no Let's Encrypt attempt and a caller can present it as ordinary input validation rather than a failed issuance  - **`CServer_Mail` can now read and change the outbound relay, not just report it.** The earlier note above — that the SASL password file is deliberately not read — no longer holds, and the reason it was reversed is worth recording: when relay authentication starts failing, the one thing nobody can answer from the outside is *which* key the server is actually presenting, and the file is the only place that answer exists. `getRelayUsername()`/`getRelaySecret()` read `/etc/postfix/sasl_passwd` (through `sudo -n` when the connection is not root), matching the entry against the configured `relayhost` rather than taking the first line, since the file may hold entries for hosts no longer in use. `providerList()` holds the presets for Mailjet, SendGrid and MailerSend — host, default port, the ports each accepts, what its two credential fields are actually *called* by that provider (Mailjet says API key/secret key, SendGrid requires the literal username `apikey`), a documentation link and the steps to obtain them — so a UI does not restate them and `testRelay()`/`applyRelay()` work from the same definitions. `testRelay()` probes in stages (DNS, TCP, STARTTLS or implicit TLS by port, then SMTP AUTH) and returns one result per stage, because a block on port 587 and a rejected key are different problems with entirely different fixes, and a single pass/fail hides which one happened. `applyRelay()` only writes after its own test passes, backs up `main.cf` and `sasl_passwd` with a dated copy first, writes the credential file with `umask 077`, runs `postmap`, and reloads postfix rather than restarting it
  - `CServer_Mail`, `CServer_Certbot` and `CServer_SshKey` identifier rename — local variables and one protected method (`pisahDaftar()` → `splitList()`) were in Indonesian; all identifiers are English now. Comments stay as they are. No behaviour change, and no public API touched
