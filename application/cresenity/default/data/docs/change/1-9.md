# Change Log 1.9

- CF
  - Fix `CElement_Component_DataTable`'s export traits (`ExportTrait.php` and `Legacy/ExportTrait.php`) reading a `$footer_field`/`$this->footer_field` property that doesn't exist — the real property (from `CElement_Component_DataTable_Trait_FooterTrait`) is `$footerFields`, an array of `CElement_Component_DataTable_FooterField` objects. Any DataTable export with the footer enabled hit a null/undefined access; now reads via `getLabel()`/`getValue()`/`getAlign()`/`getLabelColSpan()`
  - Investigated a reported `CElement_FormInput_EditorJs_Tool_ImageTool` fatal-crash report — not reproducible against current code; `ImageTool` never reads the `toolSettings.image.services` key the report described (only `EmbedTool` reads a `.services` key, from `toolSettings.embed.services`, which does exist). No fix needed
  - **Rollback:** removed the per-app "public docroot" feature (`CF::publicPath()`, root `DOCROOT/public` folder, `CHTTP_FileServeDriver`, `asset:install` console command). Apps are always served through the shared front controller now; Vite builds and framework/theme assets resolve under each app's `default/media` directory instead of a dedicated public folder per app. `CF::isIndexInApp()` is kept (still used by `CF::appCode()` for CLI/app-identity resolution) but no longer implies a separate public docroot
  - `.htaccess` hardened: block `logs/`, `.env`, `.sql`, `.key`/`.pem`, `.DS_Store`, `.php-cs-fixer.cache`, `.phpunit.result.cache`, and `TODO.md` from direct web access — found `application/aidnity/.env` and a real OAuth private key (`oauth-private.key`) were both directly web-reachable
  - New `tests/Translation/` suite (108 tests) covering `CTranslation_Translator` fallback/placeholder behavior and real `system/i18n/` data integrity; fixed a dead `en_US/filemanager.php` stub (evaluated to `int(1)`, no `return`) and a stale `%s`-style placeholder in `id_ID/core.php`'s `driver_not_found`. Removed `system/i18n/en/` (byte-identical to `en_US/`, only real consumer was `shopnest`'s bare `'en'` locale, fixed to `en_US`)
  - Moved `LanguageCode/ISO6391.php` (used by `CApp_Data::getLanguageCode()`) from the deprecated `modules/cresenity/data/` into `system/data/`, matching the CF 1.9 goal of retiring `modules/`
  - **Security:** removed `CApp_Api` and its public `/cresenity/api/...` dispatch endpoint (`Controller_Cresenity::api()`, `CApp::api()`) — a remote server-management HTTP API (git pull/checkout/discard, file listing, PHP info, domain create/delete, SSL certificate install, temp file read/delete) whose per-request auth (`CApp_Api_Method::auth()`) was fully bypassable by adding an `?auth=` query param to any request. Also removed `CApp_Administrator` and its panel controllers (`CApp_Administrator_Controller`, `_Controller_User`) — gated only by the *presence* of a client-controlled `capp-administrator` cookie, with a hardcoded MD5 password hash as the login check. Both were dead/unrouted in every app checked, but present in the shared framework and reachable by any app that wired up a controller for them. `CApp_Administrator_Fixer_Database` (an unrelated, actively-used schema-diff utility that happened to live under the `Administrator` namespace) was preserved and moved to `CDatabase_Fixer`
  - Fixed `CManager_DataProvider_ModelDataProvider` silently losing its `queryCallback` — it wrapped the callback in raw `Opis\Closure\SerializableClosure`, which hit a PHP reflection engine edge case on unserialize and silently produced `null` instead of throwing, breaking team/tenant scoping on every model-backed `SelectSearch` field with no visible error. Migrated to `CFunction_SerializableClosure`
  - Fixed a "Failed to retrieve the reflection object" crash from `CFunction_SerializableClosure_Serializer_NativeSerializer::__serialize()` — PHP's reflection engine can intermittently fail to introspect a closure's scope class via `getClosureScopeClass()`; now caught and falls back to no scope instead of crashing. Also migrated `CElement/Component/Form.php`, `CNotification/ChannelAbstract.php`, `CTrait/Element/Transform.php`, `CValidation/Rule.php`, and `CException/ContextAbstract.php` off raw `Opis\Closure\SerializableClosure` onto `CFunction_SerializableClosure` for consistency (remaining usages tracked in `TODO.md`)
  - New regression test suites: `tests/Function/SerializableClosureTest.php` (closure serialization, including the reflection-failure fallback above), `tests/Manager/ModelDataProviderTest.php` and `tests/Ajax/SelectSearch{Model,Closure}RoundTripTest.php` (the `ModelDataProvider` bug above, exercised through the real `CElement_FormInput_SelectSearch` → `CAjax_Engine_SelectSearch` ajax round trip), plus `tests/Pagination/{Paginator,LengthAwarePaginator}Test.php` and `tests/Config/CConfigTest.php`
  - Fixed `CConfig::has()` (and by extension `offsetExists()`/`isset($config[...])`) not prefixing its key with the config group the way every sibling method (`get()`/`set()`/`getMany()`) does — `isset($config['foo'])` right after `$config['foo'] = 'bar'` used to be `false`. Found while writing `CConfigTest`
  - Moved the `blockly` module's asset definition from the deprecated `modules/cresenity/config/client_modules.php` into `system/data/assets-module.php`; the vendored library files stay under `modules/cresenity/media/js/blockly/` and still resolve correctly via the existing cascading media-path lookup (`CF::getDirs('media')`) — one step towards retiring `modules/`
  - PHP 8.4 deprecation cleanup: fixed `${var}`-style string interpolation in `CDatabase_Query_Grammar` and `CSession_Factory`; fixed an optional-before-required parameter order warning in `CTrait_Compat_Element_DataTable::export_excelxml_static()` (also fixed it always passing `null` for `$sheet_name` regardless of the caller's value, due to an accidental assignment inside the forwarding call); added missing `#[\ReturnTypeWillChange]` to `CSession_NativeAdapter`'s `ArrayAccess` methods and vendored Guzzle's `CookieJar::count()`/`getIterator()`; added explicit `?Type` nullable hints to vendored League OAuth2/Event constructor parameters
  - Fixed `CException_ExceptionHandler` reporting its own file/line as the crash site for every non-HTTP exception. `prepareResponse()` wraps such exceptions in a fresh `CHTTP_Exception_HttpException`, so the wrapper's `getFile()`/`getLine()`/`getTrace()` point at `ExceptionHandler.php` rather than the code that actually threw — a real "Method setInfoText does not exist." in devcloud reported as `ExceptionHandler.php [532]` with no way to find the offending line. `renderExceptionContent()` now unwraps back to the original via `unwrapWrappedException()` before rendering; only the exact `CHTTP_Exception_HttpException` class is unwrapped, so `NotFoundHttpException` and friends still render as themselves. Noted but **not** fixed (behaviour change too broad to bundle here): `renderExceptionContent()` opens with an unconditional `return CException_LegacyExceptionHandler::getContent($e);`, making the `CF::isProduction()` / `show_debug_error` branch and the modern `CException_Renderer_ExceptionRenderer` below it unreachable dead code
- CElement
  - `CElement_FormInput_Text` converted to cres.js (`control:Text`); removed dead `$action`/`add_action()`/`buttonPosition` API and the no-op `$this->validation->validationClass()` call (also removed from remaining FormInput classes)
  - `CElement_FormInput_FileAjax` now extends `CElement_FormInput_File` (was a sibling); `acceptFile` moved to the shared parent and validated client-side. Both converted to cres.js (`control:File`, `control:FileAjax`)
  - Added translated error messages for accept-file/upload validation (`element/file.errorMessageAcceptFileNotAllowed`, new `element/upload.php` i18n group) surfaced via `cres-config` instead of hardcoded English strings in JS and `CAjax` upload traits
- CView
  - New `tests/View/` suite (174 tests) covering `CView_Compiler_BladeCompiler` end to end: all 18 `compile*Trait` files (classes, style, js, use-statement, comment, injection, fragment, raw-php, session, error, json, translation, helper, include, authorization, stack, layout, echo, loop, component, conditional), the compiler's own top-level `compileString()` pipeline (verbatim blocks, custom directives, extensions, precompilers, `aliasIf`/`check`, component-alias registration), and `CView_Compiler_ComponentTagCompiler` (`<x-component>`/`<x-slot>` tag syntax, attribute binding, class-vs-view component resolution). Found and documented (not fixed) a partitioning detail worth remembering: an `<x-component>` attribute whose name matches a class component's constructor parameter is routed into the `@component(...)` constructor-data array rather than `$component->withAttributes([...])`, so it never goes through `sanitizeComponentAttribute()`'s escaping. The rest of `CView` (`Factory`, `Finder`, `View`, `EngineResolver`, the `Component*` runtime classes) remains uncovered — tracked in `TODO.md`
  - Extended `tests/View/` with `FinderTest.php`, `EngineResolverTest.php`, and `ComponentAttributeBagTest.php` (48 more tests). **Fixed a real fatal error found along the way**: `CView_Engine_FileEngine implements CView_EngineAbstract`, but `CView_EngineAbstract` is an abstract class, not an interface — a plain PHP fatal ("cannot implement ... it is not an interface") the moment the class loads. Changed to `extends`. This made the `file` view engine (`.css`/`.html` view files) completely unusable; apparently never hit in practice since nobody had reported it.
  - **`CView` test suite complete** — added `tests/View/{ManageStack,ManageFragment,ManageLayout,ManageLoop,ManageTranslation,ManageComponent,ManageEvent}TraitTest.php`, `FactoryTest.php`, `ViewTest.php`, `ComponentAbstractTest.php`, `AnonymousComponentTest.php`, `TemplateComponentTest.php`, `DynamicComponentTest.php`, and `IconComponentTest.php` (127 more tests, 349 total in `tests/View/`). **Fixed another real bug found along the way**: `CView_Trait_ManageEventTrait::buildClassEventCallback()` referenced an undefined `$this->container` property — `CView_Factory` has no such property, only `getContainer()` (which resolves `CContainer::getInstance()`) — so any string/class-based view composer (`composer('view', 'SomeClass@compose')`, as opposed to a Closure) threw instead of working. Fixed to call `$this->getContainer()`. Also documented (not fixed) two more rough edges: `CView_Factory::setFinder()`/`$finder` are dead code (`getFinder()` and every view-resolving method call `CView::finder()` directly instead), and `CView_View::gatherData()` always reads shared data from the global `CView::factory()` singleton rather than whichever `CView_Factory` instance actually created the view — so `share()` on a manually-constructed `CView_Factory` never reaches rendered views, only sharing on the real singleton does. Also: `CBase_HtmlString` implements the plain `Illuminate\Contracts\Support\Htmlable`, not the CF-specific `CInterface_Htmlable` that `ManageComponentTrait::renderComponent()` actually checks for, so passing a `CBase_HtmlString` as a component view falls through to being treated as a view name instead of rendered as raw HTML
  - **`Opis\Closure\SerializableClosure` migration audit complete.** The real fix: patched the *vendored* `system/vendor/Opis/Closure/{SerializableClosure,ReflectionClosure}.php` directly with the same try/catch around `getClosureScopeClass()` already applied to `CFunction_SerializableClosure_Serializer_NativeSerializer` — this protects every remaining Opis consumer (including ones that `extend` Opis's class directly, which can't be migrated to `CFunction_SerializableClosure`'s composition-based design without rewriting them) from the "Failed to retrieve the reflection object" crash, regardless of which wrapper class they use. New `tests/Function/OpisSerializableClosureTest.php` covers it directly. On top of that: **fixed `c::value()`**, which only unwrapped-and-invoked `\Opis\Closure\SerializableClosure`, silently returning a `CFunction_SerializableClosure`-wrapped closure *unin­voked* instead (it isn't a `\Closure` either, so the last fallback line didn't catch it) — likely the most consequential single gap in the whole audit, since `c::value()` is used throughout the framework as the generic "resolve this, calling it if it's a closure" helper. Also **fixed `CElement_FormInput_SelectSearch_Trait_Select2v23Trait`** (the legacy select2 v2.3 `formatResult`/`formatSelection` markup generator): it only checked `instanceof \Opis\Closure\SerializableClosure`, but `setFormatResult()`/`setFormatSelection()` have wrapped closures in `CFunction_SerializableClosure` for a while now — so the format closure was never actually invoked in this legacy code path, silently falling through to raw/empty output. Migrated the remaining direct `new Opis\Closure\SerializableClosure(...)` call sites (`CJavascript::closureToJs()`, `CObservable_Javascript::createFunction()` — verified the `serialize()` byte layout is close enough for their closure-source-extraction regex to still match both wrapper types; `CElement_Depends_DependsOn`, `CElement_Component_ActionRow`, `CManager_DataProvider_{Closure,Sql}DataProvider`, `CManager_Transform_Method_ClosureMethod`, `CRouting_Route::prepareForSerialization()`, `CBot_Trait_HandlesConversationsTrait::serializeClosure()`, `CFunction`'s closure-wrapping constructor) onto `CFunction_SerializableClosure`, and added a matching dual-type check to every remaining read-only `instanceof Opis\Closure\SerializableClosure` site (`CManager_Transform_{Repository,Parser}`, `CAjax_Engine_ImgUpload`, `CDatabase_Driver_Mysqli`, the `CBot` trait's read side) so both old and newly-produced closures keep working. Left `CQueue_SerializableClosure` (extends Opis directly, for queue-payload Eloquent-model rehydration) unmigrated on purpose — see `TODO.md` — since it's now protected transitively by the vendored patch anyway
