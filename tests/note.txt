[operatorForWhere saga - ACTUALLY RESOLVED, root cause fixed properly]
Correction to both earlier notes above: my original band-aid fix (restoring
the `|| $operator === null` / `|| $value === null` fallback in
operatorForWhere()) was itself WRONG, not just fragile. The CCollection
agent's independent analysis (after it finished all its own work) was
correct: that fallback fixes the ModelCollectionTest case but BREAKS the
opposite case - a genuine 3-arg call with an intentionally-null $value
(e.g. `where($key, '=', null)`, which whereNull()/whereNotNull() rely on)
gets misinterpreted: func_num_args()===3 but $value===null triggers the
second fallback branch, which overwrites $value with the operator string
'=' instead of leaving it null. So my fix was trading one bug for another.
The REAL root cause: CModel_Collection::contains() (system/libraries/
CModel/Collection.php) always called `parent::contains($key, $operator,
$value)` with all 3 params explicitly, even when ITS OWN caller only
passed 2 (operator/value default to null but PHP still "passes" them
explicitly when you name them in the call) - this inflates func_num_args()
downstream to 3 regardless of what the original public caller gave,
which is what actually confuses operatorForWhere(). Fixed AT THE SOURCE
instead: changed that one call to `parent::contains(...func_get_args())`,
which forwards exactly as many args as CModel_Collection::contains()
itself received - preserving the true original arg count all the way
down. This lets operatorForWhere() stay a clean, unmodified, exact port of
upstream Laravel (func_num_args()===1/===2, no fallback needed) AND fixes
ModelCollectionTest correctly. Verified: ModelCollectionTest 38/38,
CollectionTest 640/640, full suite 1628 passed / down to exactly the 17
pre-existing sqlite-driver baseline failures + 5 unrelated failures in
ModelBelongsToManyTest that belong to a different, still-running agent
(expected mid-flight, not this issue).
LESSON (revised from before): when two agents' fixes to the same symptom
conflict, don't assume the first one to land is correct just because it's
"already fixed" - re-derive from first principles which one is actually
the root cause. In this case neither of my first two attempts (fallback
in Wave 1, then "wait and reapply") was the right fix; the right fix was
in a completely different file (CModel/Collection.php) that owns the
actual defect.

flagging to the team even though it wasn't "fixed": CRouting_RouteCollection

resolves its URI from c::url()->getRequest()->path() - the app's globally

bug. Root cause is CRouting_UrlFinder::getUri() (system/libraries/

is what all PHPUnit runs use, PHP_SAPI==='cli'), there's no real HTTP
request to derive a URI from, so this branch exists specifically so
tests can control "the current URI" by calling
`c::url()->setRequest($request)` first - basically this framework's
equivalent of Laravel's test-helper request binding. Not a defect, just
undocumented/non-obvious - worth a PHPDoc note on getUri() someday, but
not touching it now since it's out of scope and working as designed.

REAL BUGS FOUND AND FIXED (all confirmed via the new test suite, several
only surfaced by writing the tests - reasoning alone said the fix was
sufficient in two cases where it demonstrably wasn't, see below):
- CModel_Nested_NestedSet::isNode(): was `in_array(CModel_Nested_Trait::class,
  (array) $node)` - casting an object to array gives its PROPERTY VALUES,
  never trait names, so this was always false in real usage. This is
  actually a verified, still-open upstream bug (lazychaser/laravel-nestedset
  #538, unmerged fix PR #368 since 2019) faithfully inherited by the port,
  not introduced by it - but it still bites this codebase: every
  ->ancestors()/->descendants() relation access throws
  InvalidArgumentException('Model must be node.') via
  CModel_Nested_Relation's constructor, and whereAncestorOf()/
  whereDescendantOf() silently fall through to the "treat as raw id" branch
  when given an actual node instance. Fixed using the framework's own
  c::hasTrait() helper (which is, ironically, exactly what the dead
  Move.php file below already uses correctly).
- bootNestedTrait() never registered `deleted`/`restored` model events -
  only saving/saved/deleting/restoring were wired. deleteDescendants() and
  restoreDescendants() (both fully, correctly implemented) were therefore
  unreachable dead code: deleting a node with children left every
  descendant row orphaned in the database and never closed the lft/rgt gap
  for the rest of the tree - silent, permanent data corruption with no
  error. This is the most severe finding of the whole audit. Fixed by
  registering both events in bootNestedTrait().
- actionBeforeOrAfter() and actionRoot() never called setDepthWithSubtree()
  after moving an existing node (unlike actionAppendOrPrepend(), which
  always did) - moving a subtree via beforeNode()/afterNode()/up()/down()/
  saveAsRoot() left every descendant's `depth` column stale after a level
  change. Fixed by adding the same setDepthWithSubtree() call to both.
- setDepthWithSubtree() itself was broken for ALL three action paths
  (including the "already working" append/prepend one) in a way pure
  reasoning didn't catch - only the new tests did: it computes a depth
  DIFF (oldDepth vs newDepth) and applies it to descendants via
  ->increment(), but by the time it runs, setParent() (called earlier in
  the same operation) had ALREADY overwritten the node's own depth
  attribute to the new value - so oldDepth always read back as
  already-new, diff was always 0, and the descendant cascade never fired
  for ANY move, ever. Fixed by adding a $depthBeforeMove property that
  setParent() stashes the true prior depth into before overwriting it,
  which setDepthWithSubtree() now consumes instead of re-reading the
  (already-mutated) live attribute.
- refreshNode() only ever re-fetches lft/rgt (faithful to upstream, which
  has no depth column at all) - so even after the fix above correctly
  cascades a descendant's depth in the database, any already-loaded
  in-memory reference to that descendant stayed stale forever, since
  calling refreshNode() on it wouldn't pick up the new depth. Fixed by
  having refreshNode() additionally select+merge the depth column
  (deliberately NOT by changing CModel_Nested_Query::getNodeData()/
  getPlainNodeData(), whose 2-column [lft,rgt] shape other callers like
  whereDescendantOf() rely on feeding straight into a BETWEEN clause -
  changing that shape would have broken those. refreshNode() now runs its
  own 3-column select directly instead).
- rawNode()'s depth fallback used loose `$depth == null` instead of
  `=== null` - `0 == null` is true in PHP, so an explicitly-passed depth of
  0 (a legitimate depth for a root) would have been silently discarded and
  recomputed from the parent instead. No internal call site actually hits
  this today (all pass either an explicit non-zero depth or omit it
  entirely), so purely a defensive fix for a latent trap.
- fixTree()/rebuildTree() (fixNodes()/reorderNodes() in Query.php): each
  node's depth was derived via `rawNode()`'s fallback calling
  `static::find($parentId)->getDepth()` - a FRESH, separate query against
  whatever the parent's depth CURRENTLY is in the database. Since
  reorderNodes() is post-order (recurses into all of a node's children
  before touching the node's own row) and nothing is ->save()'d until the
  entire recursive pass finishes, a parent's freshly-recomputed depth was
  never visible to its own children's lookup - they inherited the parent's
  STALE PRE-FIX depth instead, compounding at every generation. This is
  exactly the scenario fixTree() exists to repair (a tree whose depth no
  longer matches its structure), so it could fail at the one thing it's
  for. Fixed by threading the freshly-computed depth down through the
  recursion as an explicit parameter instead of re-querying mid-fix.
- restoreDescendants() called getDeletedAtColumn() - a method that only
  exists on CModel_Deleted_DeletedTrait (Laravel's classic deleted_at
  timestamp convention, matching what upstream lazychaser itself targets).
  But bootNestedTrait()'s own usesSoftDelete() check - the thing that
  actually gates whether restoreDescendants() ever runs - specifically
  detects CModel_SoftDelete_SoftDeleteTrait (this framework's real/primary
  soft-delete convention, a `status` int column, no timestamp at all). So
  the one soft-delete flavor this trait actually detects is exactly the
  one flavor restoreDescendants() couldn't work with - a
  BadMethodCallException on every restore of a node with descendants.
  Fixed with a method_exists() branch: models using the timestamp-based
  trait keep the original "only restore descendants deleted at/after the
  parent" semantics; models using the status-column trait (no timestamp to
  compare against) just restore every currently-trashed descendant
  unconditionally - a documented behavior adaptation, not a bug once
  flagged, since there's no way to express "deleted at/after" with a
  binary flag.
