[operatorForWhere saga - ACTUALLY RESOLVED, root cause fixed properly]
Correction to both earlier notes above: my original band-aid fix (restoring
the `|| $operator === null` / `|| $value === null` fallback in
operatorForWhere()) was itself WRONG, not just fragile. The CCollection
agent's independent analysis (after it finished all its own work) was
correct: that fallback fixes the ModelCollectionTest case but BREAKS the
opposite case - a genuine 3-arg call with an intentionally-null $value
(e.g. `where($key, '=', null)`, which whereNull()/whereNotNull() rely on)
gets misinterpreted: func_num_args()===3 but $value===null triggers the
second fallback branch, which overwrites $value with the operator string
'=' instead of leaving it null. So my fix was trading one bug for another.
The REAL root cause: CModel_Collection::contains() (system/libraries/
CModel/Collection.php) always called `parent::contains($key, $operator,
$value)` with all 3 params explicitly, even when ITS OWN caller only
passed 2 (operator/value default to null but PHP still "passes" them
explicitly when you name them in the call) - this inflates func_num_args()
downstream to 3 regardless of what the original public caller gave,
which is what actually confuses operatorForWhere(). Fixed AT THE SOURCE
instead: changed that one call to `parent::contains(...func_get_args())`,
which forwards exactly as many args as CModel_Collection::contains()
itself received - preserving the true original arg count all the way
down. This lets operatorForWhere() stay a clean, unmodified, exact port of
upstream Laravel (func_num_args()===1/===2, no fallback needed) AND fixes
ModelCollectionTest correctly. Verified: ModelCollectionTest 38/38,
CollectionTest 640/640, full suite 1628 passed / down to exactly the 17
pre-existing sqlite-driver baseline failures + 5 unrelated failures in
ModelBelongsToManyTest that belong to a different, still-running agent
(expected mid-flight, not this issue).
LESSON (revised from before): when two agents' fixes to the same symptom
conflict, don't assume the first one to land is correct just because it's
"already fixed" - re-derive from first principles which one is actually
the root cause. In this case neither of my first two attempts (fallback
in Wave 1, then "wait and reapply") was the right fix; the right fix was
in a completely different file (CModel/Collection.php) that owns the
actual defect.

[Wave 6 - CRouting Route/RouteCollection tests - DONE]
tests/Routing/RouteTest.php (70) + RouteCollectionTest.php (30), 100
tests all green, zero source bugs, but ONE REAL FRAMEWORK QUIRK worth
flagging to the team even though it wasn't "fixed": CRouting_RouteCollection
::match()'s no-match/fallback path (via CRouting_RouteFinder::find())
resolves its URI from c::url()->getRequest()->path() - the app's globally
bound "current request" singleton - INSTEAD OF the $request argument
actually passed into match(), whenever CF::isTesting() is true (which it
is under this repo's own phpunit.xml, APP_ENV=testing). Practical impact:
naive `$routeCollection->match($someRequest)` calls could silently
mis-route to whatever URI happens to be globally bound (defaults to '/')
instead of the request you actually passed in, specifically under test
conditions - could mask real routing bugs in application-level tests
elsewhere in this codebase (or any app built on this framework) without
anyone noticing, since it fails "successfully" rather than throwing.
Worked around in the new tests via `c::url()->setRequest($request)`
before every match() call.
FOLLOW-UP (I investigated this myself): confirmed intentional, not a
bug. Root cause is CRouting_UrlFinder::getUri() (system/libraries/
CRouting/UrlFinder.php:10): `if (CF::isTesting()) { return
ltrim(c::url()->getRequest()->path(), '/'); }`. Under plain CLI (which
is what all PHPUnit runs use, PHP_SAPI==='cli'), there's no real HTTP
request to derive a URI from, so this branch exists specifically so
tests can control "the current URI" by calling
`c::url()->setRequest($request)` first - basically this framework's
equivalent of Laravel's test-helper request binding. Not a defect, just
undocumented/non-obvious - worth a PHPDoc note on getUri() someday, but
not touching it now since it's out of scope and working as designed.
